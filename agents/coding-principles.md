# コーディングの原則

オーナーが、コードを書くとき・レビューするときに大事にしていること。**コーダー**が従い、**レビュワー**が確かめる。言語ごとの細かい決まりは、別にある(未整理。下記の未確定)。

## 最上位: 一貫性

- **最も重要視するのは「一貫性」**。プロジェクト全体で統一されていることが大事。たとえ変な書き方や名前でも、全体で統一されていれば、後から参加した人は同じものに対して悩まない。
- **プロジェクトの既存の書き方・規約が、この原則集より優先する**。プロジェクトの規約が無い、または曖昧なところで、この原則集を使う。
- どちらで書いても一貫性はある書き方で、トレードオフが生じるときの判断軸は、**シンプルであるか**。

## 保守を第一にする

- **今作りやすいコードではなく、数年保守できるコードを書く**。開発の時間より保守の時間のほうが圧倒的に長い。多少苦労してでも考え抜いて、楽な方に流れない。
- **コメントが必要なコードの時点で、読みづらいコードである**。コメントで補う前に、コードを読みやすくする。
- **拡張しやすく、修正に閉じている**(開放閉鎖)。
- **コメントに、ドキュメントへの参照を書かない**(確定)。文書名、節番号、ADR や指摘の番号などを、コメントにも、docstring にも、テストの名前にも書かない。文書は改名・削除・再編されるので、参照は腐る。コメントは、そのコードだけで読める内容(理由、前提)を直接書く。

## 構造

- **インデントが多くならない工夫をする**。例: スコープ全体が `if () {}` なら、余事象で早期リターンする。仕方のない場面もあるので、何段まで、という指定はしない。
- **try-catch をネストしない**。必要なら関数を分ける。`finally` を使いたいだけで `try` を書かない。
- **if 文はワンライナーで書かない**(ログを出す、中に入っているかを確かめる、などをするため)。
- **できる限り純粋関数にする**。
- **制約の厳しいレイヤーのロジックが多くなるように、できる限り引き込む**。
- **処理をブロック単位で考えて、空行を入れる**。ブロックは、短い言葉で説明できるラベルをつけるイメージ。例:

  ```ts
  const user = repo.fetchUser(id);
  if (user.isAdmin) {
    throw new Error();
  }
  ```

  この 3 行のまとまりに、「一般ユーザー取得」というラベルがつくイメージ。ブロック単位でプログラムを認識する。

## 名前

- **変数名は、シンプルで、分かりやすいものにする**。
  - `user.userName` のような冗長な名前をつけない。
  - 配列の変数は複数形にする。
  - `info`、`data` のような、まったく意味のない名前をつけない。
- **寿命の長い変数は、しっかり名前をつける。寿命の短い変数は、1、2 文字にする**。
  - 短い例: 高階関数に渡す短いコールバックの引数の `s`(文字列)、配列の高階関数の要素を表す `e`。
  - **50 行以上生きるなら、寿命が長い**。VS Code などで 1 画面に宣言と使用箇所が収まっているなら、寿命は短い(目線を上下するだけで意味が分かる)。スクロールを伴うほど離れていると、レビューしづらい。
- **関数は、必ず「動詞 + 対象(+ 修飾)」**。例: `parseNumberSafe(v: unknown, fallback = 0)`。

## 引数と並び

- **引数の順番は、呼ぶ側が自然に書ける順にする**。
- **順不同な配列は、アルファベット順にする**。`useEffect` の deps は、あくまで一例。

## 冗長さを受け入れる(確定)

- **冗長さと、ファイル数の多さは、承知のうえの代償**。クリーンアーキテクチャとリーダブルコードは、管理性が最高とは言えない。それでも採るのは、依存の向きの強制力と、冗長であるがゆえに、つなぎ目がバッファとなって、柔軟さを生むから。
- **基準は、人間が一度に視界に入れて読み切れる量**。1 ファイルを単純にし、ファイルツリーを見るだけで、構造と責務が分かるようにする。視界に入る情報量が、自然と少なくなる仕組みにする。人間の演算能力は、これが最大である(書く側の演算能力を基準にしない)。
- **短さ、ファイル数、記述量を、良し悪しの基準にしない**。「まとめれば短くなる」「共有すれば減る」は、境界を消す提案であり、理由にならない。境界、変換、専用の型は、省かない。
- **1 ファイルが、視界に収まらなくなったら、概念ごとにファイルを分ける**。

## 操作の入出力と、DTO(確定)

- **操作(ユースケース、API など、外から呼ばれる単位)ごとに、専用の Input と Output を持つ**。複数の操作で共有しない。共有すると、ある操作に値を足したとき、ほかの操作の約束も動く。
- **Input と Output は、基本オブジェクトにする**。配列、プリミティブ、エンティティ、空(`void`)をそのまま返さない。例: `Repo[]` ではなく `{ repos: Repo[] }`。将来フィールドを増やすとき、変更がその操作のファイルに閉じ、呼び出し側は足された値を無視できる(開放閉鎖)。値が無いときも、空のオブジェクトを返す。
- **Output 自体は DTO ではない**。その中に、エンティティなどを表すデータがあるなら、**その部分が DTO**。
- **DTO は、内側の型(エンティティ、ユースケースで使うデータ型)の、外の世界での姿**。内側と外側の間に置くバッファで、内側の変更が、利用者に直接伝わらないようにする。外から内、内から外へ、境界で変換・逆変換する。DTO は、内側では使わない。
- **外の層の Input / Output は、対応する内側の操作の Input / Output と、1 対 1 で対応する**。変換は、境界の層が行う。

## エンティティのフィールドの順番

エンティティのようなクラスや構造体を定義するとき、フィールドは次の順に並べる(確定)。

1. `id`
2. `createdAt`、`updatedAt`(ほぼすべてのエンティティにつくため)
3. 何かに属するなら、その親を表すもの
4. `name`(id 以外に、このオブジェクトを表すもの。一意性の高いものの順)
5. オブジェクト固有のフィールド
6. 関連する他のオブジェクトそのもの、またはそれを表すもの(複数あるなら、アルファベット順)

## この原則集の位置づけ(確定)

- **原則は原則**。プロジェクトによって変わるものは、原則と呼ばない。この原則集は、**プロジェクトごとに差し替えない**。
- **プロジェクトによって変わるもの**(使う言語の固有の書き方、プロジェクトの規約)は、**プロジェクトコンテキスト**に書く。最上位の「一貫性」により、プロジェクトの既存の書き方が優先する。
- **言語ごとの決まりのうち、プロジェクトによらず守る原則に近いものは、この文書に言語別の節として足してよい**。
