# デザイン設計担当

ロール一覧は [../roles.md](../roles.md)。状態 **デザイン設計** を担う。次の状態は機能設計。

## 役割

状態 **デザイン設計** で、**デザイン設計**を出す(確定)。デザインが必要なチケットだけ動く(デザインの要否は DEV リファインで決める。不要なら anvil がこの状態をスキップする)。**機能設計より先**で、機能設計の前提になる。

## 入力(確定)

- チケット(AC、実装方針、エントリ)。
- **デザインシステム**。
- **既存の画面**。
- プロジェクトコンテキスト。

## デザイン設計に書く内容(確定)

画面の見た目と振る舞いを、デザインシステムと既存の画面に沿って、具体的に決める。
- 画面の構成とレイアウト(どこに何を置くか)。
- 使うコンポーネント(デザインシステムのどれを使うか。新規が要る場合は、その旨)。デザインシステムが無いプロジェクトでは、既存の画面との一貫性に従う。
- 状態ごとの見え方(通常、読み込み中、空、エラー、無効など)。
- 操作の流れと画面遷移。
- 文言とメッセージ。
- 既存の画面との一貫性(違うところがあれば、その理由)。

書かないこと:
- 実装の方法(コードの構成、技術)。実装方針や実装の仕事。
- 機能の振る舞いの詳細(機能設計担当の仕事)。

AC のそれぞれが、デザインのどこで満たされるか分かるように書く(テスト設計と動作確認の入力になる)。

## 出力(確定)

- **このフェーズでは、チケットのエントリ(本文)以外の出力は作らない**。デザインツールのファイルなどは、このフェーズでは作らない。
- 書き手はエージェント。エントリのロールは「デザイン設計担当」。

## 申し送り(確定)

- **なければ書かない**。機能設計担当へ、特に伝えることが無ければ、省略してよい。

## 細部(確定)

- **本文の形**(見出し、書き方): 固定しない。ロール別ページで制御する。ロール別ページが無ければ、要素さえ含めば形は自由。
- **既存の画面の見方**(コード、スクリーンショット、storybook など): ロール別ページに書く(ロールの定義にツール名は書かない)。
- **デザインシステムが無いプロジェクト**: 既存の画面との一貫性に従う。新しいパターンを増やすときは、承認待ちフラグで聞く。
