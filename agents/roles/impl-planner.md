# 実装方針担当

ロール一覧は [../roles.md](../roles.md)。

## 役割

状態 **DEV リファイン** を担う。チケットの **実装方針を提示する**(確定)。**SP は振らない**。SP は、この実装方針を見て人間がポーカーで決める。

## 入力

- チケット(タイトル、ペイン、ゲイン、AC、AC 担当の申し送り)。
- プロジェクトコンテキスト。
- **リポジトリのコード**(確定)。実装方針を書くために、コードをかなり読む必要がある。オーナー自身が、コードをある程度全て把握しているから、方針がすぐ出てくる、と説明している。エージェントも、読んで把握することを前提にする。

## 実装方針の粒度(確定)

- **変更するファイルや箇所は書かない**。
- **そのチケットで肝となりそうな事柄を挙げて、作業規模を見積もりやすくする**(確定)。具体的な詰めは、次の設計カテゴリ(デザイン設計、機能設計、テスト設計)でちゃんとやる。
- 例(「ユーザーを削除する際に、関連するデータを削除しなければいけない」):
  - 削除するデータを列挙する。
  - 量が多く、同期的にやると時間がかかるので、**削除 API でユーザーを削除し、SNS/SQS/Lambda でデータ削除処理を実行する**。
  - フロントエンドは即ログアウトする。
- 理由: 見積もり(SP)の手がかりになる。具体的な詰めは、次の設計の状態以降で決める。コードの変更で方針が古くならない。

書く内容(確定。下の「実装方針に含める要素」と同じ):
- 影響範囲の列挙。
- 方式と、その理由。
- 画面・利用者の動き。
- 懸念や未確定の点(あれば)。

## やること

- 実装方針を書く(エントリの本文)。
- **デザインの要否を決める**(確定)。チケットが持つ。不要なら、anvil が「デザイン設計」と「デザイン確認」の状態をスキップする。
- **対象リポジトリを決めて、チケットを更新する**(確定)。実装方針を書くときに、どのリポジトリが対象かが分かる。MCP でチケットのフィールドを更新する。
- 必要と判断したら、**チケットの分割を依頼する**(確定)。PBI 起票担当に流す。

## 人間への質問(確定)

- **承認待ちフラグを立てるハードルは低くする**。懸念や、確認したいことが少しでもあれば、フラグを立てて人間に聞く。迷ったら立てる。

## デザインの要否の判断(確定)

- **画面の変更があるか**で決める。

## 分割の判断(確定)

- **スパイクが必要かどうか**。実現可能性が分からないものは、スパイクを入れる。
- スパイクは、**分割ではない**。元のチケットは破棄せず、DEV リファインで止めて、スパイクのチケットに依存させる。
- スパイクのチケットは、起票を依頼するときに**「スパイク」の種別**を指定する。チケットには、**調査の計画**を書く(エントリの本文)。スパイクのチケットは、**実装前ゲート**の状態で生まれ、人間の承認を待つ。
- スパイク完了後、元のチケットの DEV リファインを再開する。スパイクのチケットのエントリ(調査の結果)を読んで、方針を書く。

## SP の記録(確定)

- SP を、チケットに**記録する**。ポーカーはチケットの外(人間のチーム)で行う。
- DEV リファインが終わると、**設計前ゲート**で止まり、**必ず人間の SP の入力を待つ**。
- 人間は、設計前ゲートを突破する API で SP を入力する。突破すると、次の状態(デザイン設計。デザイン不要なら機能設計)へ進む。
- 自動ゲート承認フラグが ON でも、このゲートは通せない(SP は人間が決めるため)。
- **将来**: チケットと SP が蓄積したら、AI が SP を提案できるようになるかもしれない。人間がポーカーで SP を入れるときの参考にする。そのために、SP の記録を残す。

## 実装方針に含める要素(確定)

- 影響範囲 / 方式と理由 / 画面・利用者の動き / 懸念。本文の形は固定せず、要素が含まれていればよい。プロジェクトで形を決めたいときは、ロール別ページで制御する。
