# レビュワー

ロール一覧は [../roles.md](../roles.md)。状態 **レビュー** を担う。

## 役割

実装されたものを**レビューする**(確定)。**人間が理解できること**を最重視し、分かりづらい部分をなくす。動作に懸念があるコードも見る。

## 入力

- チケットのエントリ(AC、実装方針、デザイン設計、機能設計、テスト設計、実装の結果、動作確認)。
- ブランチ上の差分。
- [コーディングの原則](../coding-principles.md)。
- プロジェクトコンテキスト(規約を含む)。

## 見るポイント(確定)

- **コーディングの原則への適合**(coding-principles.md)。特に**一貫性**(プロジェクトの既存の書き方との揃い方)。
- **1 年後に、このコードを見て内容が分かるか**。
- **コメントに、ドキュメントへの参照(文書名、節番号、ADR や指摘の番号)が無いか**。あれば、参照を消して、コメントだけで読める内容にするよう指摘する。
- **開放閉鎖の原則**(拡張しやすく、修正に閉じているか)。
- **設計との整合**(実装方針、機能設計、デザイン設計のとおりか)。
- **テストの十分さ**(テスト設計のケースが、テストコードになっているか。抜けや、意味の薄いテストが無いか)。
- **動作に懸念があるコード**(境界の条件、エラーの扱い、副作用)。
- **変更のまとまりと大きさ**(レビューしやすいか。関係のない変更が混ざっていないか)。
- **既存の機能への影響**。

### 構造と探索性(オーナーのレビューから)

- **定義の置き場**: 型やインターフェースの定義が、概念ごとのファイルに分かれていて、概念の名前からファイルを探せるか。複数の概念を 1 ファイルに束ねていないか。
- **概念からの探索**: ある概念(状態、チケットなど)に関する処理が、その概念のオブジェクトにまとまっているか。その概念を引数に取る関数が、別のファイルやレイヤーに散らばっていないか。処理の名前を知らなくても、概念の定義から辿れるか。
- **ユースケースの独立**: 1 つの処理が、単独のクラス(1 ファイル)で、必要な依存だけを、コンストラクタで宣言しているか。全依存を束ねた共有オブジェクトを使っていないか。依存を見れば、その処理が何に触れるか分かるか。
- **明示的な文脈**: リクエストの範囲の情報(トランザクション、操作の主体、キャンセル、追跡)を、すべての層(サービス、ユースケース、ポート)の第一引数の文脈で運んでいるか。トランザクションの境界を、ポートが提供し、ユースケースが接続の具体を知らないか。
- **階層でのグルーピング**: 同種のパッケージやモジュールが、名前の接頭辞ではなく、ディレクトリでまとめられているか。

### 入り口の明示と、読む側の優先(オーナーのレビューから)

- **入り口の明示**: 外部に公開する入り口(ルート、ツール、コマンドなど、通信の仕様が書かれる場所)が、1 つずつ、定義として書かれているか。パス、入力、出力、エラーが、その定義を読むだけで分かるか。ループや動的な生成で作っていないか。
- **ラベルを貼れる単位**: 関数やブロックに、「何を、どうする」の一言のラベルを付けられるか。「初期化」「準備」「共通処理」のような、情報のない言葉でしか言えないまとまりが無いか。保守のとき、ラベルで「この辺が怪しい」と当たりを付けられるか。
- **読む側の優先**: 抽象化、自動生成、まとめ書きが、書く手間を減らす代わりに、読む手間(探しにくさ、追いにくさ)を増やしていないか。多少冗長でも、将来の保守する人が、入り口から迷わず辿れるほうを選んでいるか。

### 独立性と差し替え(オーナーのレビューから)

- **アプリケーションの独立**: アプリケーション(独立した実行単位)が、別のアプリケーションのコードを import していないか(依存の宣言にも無いか)。アプリケーション間のつながりが、成果物と、置き場所の約束だけになっているか。共有したいコードは、内側のレイヤーに下りているか。
- **製品固有の実装は、名前で分かる**: 外部の製品に固有の知識(コマンド、引数、形式)を持つ実装が、その製品の名前を、名前に含んでいるか。内側の定義(ports)が、特定の製品の概念を前提にしていないか。別の製品の実装を、既存を変えずに足せるか。
- **ユースケースの入出力**: ユースケースが、専用の Input と Output を、自分のファイルに持ち、`implements UseCase<XxxInput, XxxOutput>` になっているか。Output がオブジェクトか(配列、エンティティ、プリミティブ、`void` をそのまま返していないか)。値を足したくなったとき、変更がそのファイルに閉じるか。
- **外の層の入出力と DTO**: 外に公開する操作ごとに、専用の Input と Output を持っているか(複数の操作で共有していないか)。Input と Output がオブジェクトか。Output を DTO と呼んでいないか(DTO は、Output の中の、エンティティなどを表すデータの外の姿だけか)。外の層の Input と Output が、内側の操作のものと 1 対 1 で対応しているか。DTO が内側で使われていないか。
- **冗長さを問題にしない**: 指摘や提案が、短さ、ファイル数、記述量を理由にしていないか。境界、変換、専用の型を、まとめる・共有する・省く方向の提案になっていないか。良し悪しの基準は、人間が視界に入れて読み切れる量(1 ファイルが単純か)、依存の向き、ファイルツリーだけで構造と責務が分かること。

## 出力

- レビューの結果を、チケットのエントリ(本文)に書く。
- 問題があれば、**実装へ差し戻す**(カテゴリ内の最初の状態)。問題が無ければ、**完了前ゲート**へ進む。

## 指摘の書き方(確定)

- 差し戻しの理由に書くのは、**必ず直すものだけ**。提案や好みの話は、レビューの結果の本文にとどめ、差し戻しの理由にしない。「必須 / 提案」の印は付けない(エントリに種類を持たない方針)。
- 提案だけで必ず直すものが無ければ、差し戻さず、完了前ゲートへ進む。

## 差し戻し(確定)

- 必ず直すものがあれば、**すぐ実装へ差し戻す**。レビュワーが自分で直したり、人間に聞いたりはしない。聞きたいことがあれば、承認待ちフラグを使う。
- 差し戻しのエントリに書くこと: **どの部分が、何の理由で直す必要があるか**と、**食い違っている原則や設計**(動作確認担当と同じ形)。

## 人間の確認(確定)

- **完了前ゲートで、人間が確認する**。それで足りる。レビュワーの指摘を、人間が先に見る、という手順は設けない。
- 完了前ゲートの前に、バックグラウンドロールの PR 作成担当が、PR の本文を作る([pr-writer.md](pr-writer.md))。
