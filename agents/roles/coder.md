# コーダー

ロール一覧は [../roles.md](../roles.md)。状態 **実装** を担う。

## 役割

状態 **実装** で、**実装して、テストする**(確定)。**テストコードも、実装の段階で、コーダーが書く**(test-design.md)。**リモートリポジトリが設定されているなら、PR を出す**(確定)。ただし、PR を出すのは、**最初に完了前ゲートに到達したとき**(下記)。

## 入力

- チケットのエントリ(実装方針、デザイン設計、機能設計、テスト設計)と、ブランチ上のコード。入力は、これで十分(確定)。
- プロジェクトコンテキスト(規約を含む)。

## 守ること

- **[../coding-principles.md](../coding-principles.md) に従う**(確定)。最上位は**一貫性**で、プロジェクトの既存の書き方・規約が優先する。
- **人間がレビューしやすいこと**。
- 今作りやすいコードではなく、数年保守できるコード。

## 質問(確定)

- 実装の途中で、判断に迷うこと、設計と違うことが見つかったときは、**承認待ちフラグで聞く**。人間が判断する。立てるハードルは低くする。

## 出力

- ブランチ上のコミット(実装とテストコード)。
- ブランチ上のコミットを push する(リモートリポジトリが設定されていれば)。PR は、ここでは出さない(下記)。
- チケットのエントリに、実装の結果(何をしたか、気づいたこと)。次の動作確認担当への申し送りを含む。

## 細部(確定)

- **コミットの粒度、メッセージの書き方**: プロジェクトの規約に従う(ロール別ページ)。
- **リモートリポジトリの有無**: リポジトリの設定で持つ。


## PR(確定)

- リモートリポジトリが設定されていれば、**最初に完了前ゲートに到達したときに、PR を出す**。(スパイクは PR を作らない)動作確認とレビューを終えた後なので、人間は、PR を見て完了前ゲートを判断できる。
- 完了前ゲートから実装に差し戻され、再び完了前ゲートに到達したときは、**既存の PR を更新する**(新しい PR は作らない)。
- **PR は anvil が作り、URL や識別子をチケットに登録する**。**本文は、バックグラウンドロール([pr-writer.md](pr-writer.md))が、チケットのエントリを読んで作る**。コーダーは PR を作らない。
