# チケットのライフサイクル

チケットは、起票されてから完了するまで、決まった**状態**を順に流れる。人間が止める場所は**ゲート**と**承認待ちフラグ**だけで、それ以外は anvil が次のロールのエージェントへ受け渡す。

この文書は、チケットの一生を説明する。エージェントの起動と終了は [エージェントのライフサイクル](agent-lifecycle.md)(これから書く)、HTTP / MCP / CLI の操作は各リファレンスを参照。状態の定義の実装は [`packages/entity/src/state.ts`](../packages/entity/src/state.ts)。

## 1. 全体の流れ

```mermaid
flowchart LR
  TODO --> refine[リファイン] --> devrefine[DEV リファイン] --> G1{{設計前ゲート}}
  G1 --> ui[デザイン設計] --> func[機能設計] --> test[テスト設計] --> G2{{実装前ゲート}}
  G2 --> impl[実装] --> fv[機能動作確認] --> uv[デザイン確認] --> review[レビュー] --> G3{{完了前ゲート}}
  G3 --> DONE[完了]
```

| カテゴリ | 状態(★はゲート) | 担当ロール |
|---|---|---|
| 着手前 | ★TODO | なし |
| リファイン | リファイン / DEV リファイン / ★設計前ゲート | AC 担当 / 実装方針担当 / なし |
| 設計 | デザイン設計 / 機能設計 / テスト設計 / ★実装前ゲート | デザイン設計担当 / 機能設計担当 / QA・QE / なし |
| 実装 | 実装 / 機能動作確認 / デザイン確認 / レビュー / ★完了前ゲート | コーダー / 機能動作確認担当 / デザイン確認担当 / レビュワー / なし |
| 完了 | 完了 | なし |

- 1 つの状態に、担当ロールは 1 つ。ゲート、TODO、完了にはエージェントがいない。
- 各カテゴリの終わりに、ゲートがある。
- 「〇済」「〇中」の状態は持たない。エージェントがいるかどうかで、順番待ちか着手済みかを見分ける。

## 2. 起票

- 起票は、**簡単なやりたいこと**を渡すと、PBI 起票担当がタイトル・ペイン・ゲイン・AC などに整えて行う。整える項目は、プロジェクトコンテキストで決まる。
- 既定の開始状態は TODO。API では、任意の状態から起票できる。TODO 以外で生まれたチケットは、その状態のエージェントを起動する(ゲートで生まれたときは起動しない)。
- チケットは、タイトル、内容、種別(§7)、状態、SP、デザインの要否、slug、対象リポジトリ、依存関係、2 つのフラグ(§4)、PR の識別子を持つ。Jira のタイプ(ストーリー、タスク、バグ)は区別せず、同じフローで回す。

## 3. 状態とゲート

### 3.1 ゲート

| ゲート | 突破するもの | 突破すると |
|---|---|---|
| TODO | 人間、または人間に頼まれた Claude | リファインへ。依存先が未完了なら止まる(§6) |
| 設計前ゲート | 人間が **SP を入力**して | デザイン設計へ(デザイン不要なら機能設計へ)。このとき**ブランチを切る**(§8) |
| 実装前ゲート | 人間が承認して | 実装へ。自動ゲート承認フラグが ON なら、判断なしで突破 |
| 完了前ゲート | 人間が承認して | 完了へ。**必ず止まる** |

- ゲートごとに、突破する API が別にある。
- 設計前ゲートと完了前ゲートは、自動では通らない。SP は AI が振らず、人間が AI の実装方針を見てポーカーで決める。
- AI は、ゲートを通すかどうかを判断しない。判断が欲しいときは、承認待ちフラグで人間に聞く。

### 3.2 状態の進み方

担当のエージェントが作業を終えると、**成果物をエントリに残して、次へ進める**。進めるときに、次のエージェントへの**申し送り事項**を添えられる。anvil は次の状態のエージェントを起動し、起動に成功してから、前のエージェントを終了する。

デザインが不要なチケットは、anvil が「デザイン設計」と「デザイン確認」を飛ばす。要否は DEV リファインで決まる。

### 3.3 成果物とエントリ

各フェーズの成果物(実装方針、設計、テスト設計など)、申し送り、差し戻しの理由、質問と回答は、すべて**エントリ**として保存する。

- エントリは追記のみで、書き換えない。1 つのチケットに多数ある。
- 項目は、フェーズ(状態)、ロール、書き手(人間かエージェント)、本文、作成日時。
- エージェントには、既定で**直近 3 件**と**総件数**を渡す。それ以上は MCP で読める。
- 差し戻して同じ状態をやり直すと、エントリが増える。前の情報は残る。

## 4. フラグ

チケットは 2 つのフラグを持つ。

**承認待ちフラグ**(途中の質問)
- 担当のエージェントが、どの状態でも立てられる。確認したいことがあれば、ためらわず立てる。
- 立つと、チケットは**人間が回答するまで、その状態で止まる**。エージェントは終了せずに待つ。
- 質問と回答は、エントリの本文に書く。回答するとフラグが下り、同じ状態が続く。承認や却下といった種類は持たない。
- ゲートでは使わない(ゲートは別の仕組み)。

**自動ゲート承認フラグ**
- 起票時に ON にしておくと、**実装前ゲートだけ**を、判断なしで突破する。
- 設計前ゲートと完了前ゲートは対象外。

## 5. 戻しと破棄

- 状態は、**後ろへはどこまでも戻せる**(前へは戻せない。TODO へも戻せない)。人間も、どのロールの AI も戻せる。戻すときは**理由を記録**する(エントリ)。
- 戻り先の指定がなければ、**今の状態のカテゴリの最初の状態**に戻る。

  | 戻す元 | 既定の戻り先 |
  |---|---|
  | DEV リファイン、設計前ゲート | リファイン |
  | 機能設計、テスト設計、実装前ゲート | デザイン設計(デザイン不要なら機能設計) |
  | 機能動作確認、デザイン確認、レビュー、完了前ゲート | 実装 |

- 差し戻すと、前のエージェントを再開せず、**新しいエージェントを起動**する。新しいエージェントは、戻した理由を含む直近のエントリを読む。
- 差し戻しの回数は、特別扱いしない。詳細画面に回数を出す。
- チケットは、いつでも**破棄**できる。破棄は削除で、状態としては持たない。ブランチとワークツリーは自動では消さず、人間に知らせる。

## 6. 分割と依存

- AC 担当と実装方針担当は、チケットを**分割**できる。分割は**起票の依頼**で行い、PBI 起票担当が新しいチケットを起票する。
- 依頼は、元のチケット、新しいチケット(やりたいこと、種別、開始状態、依存先)、元を破棄するかのフラグを受け取る。分割では破棄 ON。**元のチケットは、新しいチケットがすべて起票された後に**、anvil が破棄する。起票が途中で止まっても、元は残る。
- 親子関係は作らない。代わりに**依存関係**を作る。「A が完了するまで、B は着手できない」。依存先が未完了の B は **TODO で止まる**。
- 依存先が完了しても、B は自動では進まない。TODO のまま「着手可」の印を付け、人間に知らせる。

## 7. 種別

種別は、停まる状態の並び(フローの形)を決める。起票を依頼するときに決め、指定がなければ「標準」。

| 種別 | 流れ |
|---|---|
| 標準 | §1 のすべての状態とゲート |
| スパイク | **実装前ゲート**で生まれ、実装 → 完了前ゲート → 完了。ブランチも PR も作らない |

### スパイク

実現可能性が分からないときの、調査用のチケット。

1. 実装方針担当が、DEV リファインの途中でスパイクが必要と判断し、スパイクの起票を依頼する。
2. 元のチケットは DEV リファインで止まる(スパイクに自動で依存する)。元は破棄しない。
3. スパイクは、調査の計画が入った状態で実装前ゲートに生まれる。人間が承認すると、調査(実装)に進む。方針を変えたいときは、機能設計に差し戻す。
4. 完了前ゲートで人間が承認すると完了し、元のチケットの DEV リファインが再開する。実装方針担当は、調査の結果(エントリ)を読んで方針を書く。

## 8. ブランチとワークツリー

- **ブランチは、設計前ゲートの突破時に anvil が切る**。名前はチケットの **slug**。対象リポジトリのすべてに切る。これで、設計の間にプロジェクトのツール(openspec など)を使え、実装前ゲートで差分を確認できる。
- 対象リポジトリは、DEV リファインで実装方針担当が入れる。**未設定なら、設計前ゲートは突破できない**。
- ブランチの元は、リポジトリごとの**デフォルトブランチ**。
- slug は、同じプロジェクト内で重複できない。ブランチを切る前なら変更できるが、切った後は変えられない。リポジトリ側に同名のブランチがあれば、突破を止めて人間に知らせる。
- **ワークツリー**は、チケットごと・リポジトリごとに、ブランチと一緒に作る。完了時にワークツリーを削除する(ブランチは残す)。
- 差し戻しても、ブランチは残る。設計前ゲートを再び突破するときは再利用する。

## 9. 完了

完了前ゲートに着くと、anvil が **PR を作り**、チケットに登録する(リポジトリごと)。人間が承認すると、チケットは完了する。

anvil は**マージしない**。PR のレビューとマージは、チームの通常の流れで人間が行う。完了後に直しが出たら、新しいチケットとして起票する。

## 10. 状態の履歴

anvil は、すべての状態の変更を**履歴**に残す(前の状態、後の状態、実行者、日時)。実行者は、人間、ロール、anvil の自動のいずれか。これで、自動ゲート承認での突破や、差し戻しの回数が分かる。戻した理由は、履歴ではなくエントリに書く。
